## Design Specificity Verdict

**LLM assessment:** PARTIAL but credible. Progress output expresses the Minimal Measuring Instrument direction through a fixed field column, restrained semantic color, a single-screen report, and a measurement bar. Search and view are less authored: search metrics are a long one-line payload, view has no section treatment or labels, and the error/missing-profile states lack the same calm hierarchy. The interface is product-specific in its use of days and life expectancy, but the secondary flows still feel like formatted debug output.

**Deterministic scan:** `detect.mjs --json src/main.rs` exited 0 with `[]`; zero findings and no false-positive rules. This detector is markup-oriented and does not evaluate terminal layout, copy, ANSI behavior, or cognitive load, so a clean result is not evidence that the TUI is finished.

**Visual overlays:** Not applicable. This is a native terminal CLI, not a browser surface; no browser, overlay injection, or live server was run.

## Overall Impression

The progress report now has a clear instrument language, but the system stops one pass short of a coherent terminal product. The biggest opportunity is to make progress, search, view, and failure states share one explicit output grammar—especially for users reading through a pipe or recovering from an invalid query.

## What's Working

- The fixed two-space indentation and label column make the primary report scannable.
- The `LIFE PROGRESS` title, divider, percentage, and bar create a clear focal order without decorative UI chrome.
- The day-based metrics and restrained `Keep moving.` close give the product a distinct, sober ritual.

## Priority Issues

### [P0] Output mode and script contract are implicit

**Why it matters:** Alex needs fast terminal reading, while Sam may redirect output to logs or another command. ANSI and Unicode behavior, stderr separation, and stable field labels are not an explicit contract.

**Fix:** Detect interactive output explicitly, honor `NO_COLOR`, and provide a readable ASCII/plain mode for redirected output. Keep labels and field order stable.

**Suggested command:** `$impeccable harden`

### [P1] Search and view do not share the progress report grammar

**Why it matters:** Search uses grouped rows, while view prints a raw name and a dense metric line. Users must relearn the visual language for related country data, and long country names/terminal widths can become hard to scan.

**Fix:** Give view the same title/divider treatment as search and use a fixed metric layout that degrades cleanly at narrow widths. Make the displayed nation canonical where the data layer has normalized it.

**Suggested command:** `$impeccable layout`

### [P1] Empty and missing states stop without enough recovery context

**Why it matters:** `No matches` only says to try a broader name; a missing profile names a path but not how to create or inspect a valid profile. First-timers reach a dead end.

**Fix:** Include the failed query and one concrete next command (`life-progress-cli search chi`, `life-progress-cli --help`, or the profile TOML shape) while preserving stderr semantics.

**Suggested command:** `$impeccable clarify`

### [P2] Input normalization hides mistakes

**Why it matters:** `fuzzy_search_nation_parser` returns `Common` when nation input cannot resolve, and `gender_parser` treats every value other than `0` as male. The displayed result can be valid-looking but not what the user entered.

**Fix:** Reject unknown nation and gender values with actionable errors; reserve `Common` for an omitted nation, not an invalid one.

**Suggested command:** `$impeccable harden`

### [P2] Documentation and output have drifted

**Why it matters:** README examples are part of the first-run experience; stale inline search examples undermine trust in an otherwise deliberate output system.

**Fix:** Keep one canonical sample for progress, search, view, and profile-missing states, generated from the current output grammar.

**Suggested command:** `$impeccable document`

## Persona Red Flags

- **Alex (Power User):** Flags are efficient, but there are no explicit machine-readable/plain-output guarantees, no `NO_COLOR` contract, and no shortcut for the common “search then view” flow. A long search result line slows scanning.
- **Sam (Accessibility / low vision / keyboard):** Color distinguishes matches, completion, and errors, while Unicode blocks may render inconsistently. The output needs redundant textual meaning and a plain/ASCII fallback.
- **Jordan (First-Timer):** `Common` and `All` are unexplained, `view` has no field labels, and a no-match result does not show a concrete next command or nearby suggestions.

## Minor Observations

- `print_notion_error` is misspelled internally, which increases maintenance friction.
- Leading blank lines and a trailing motivational line make output less composable in scripts.
- Search result ordering is not visibly numbered, so a long result set has weak scan anchors.
- `indices.contains` is linear per character; this is not a visible UX problem but is easy to improve while touching the renderer.

## Questions to Consider

- Is `Keep moving.` the right ending for a deliberately clinical measuring instrument, or should the close remain purely factual?
- Should `search` return a ranked, numbered shortlist that can feed directly into `view`?
- What is the intended contract when output is piped to cron, logs, or another program?
